# Adding or changing a model

Start with a written scientific specification. State the question, inputs,
assumptions, outputs, ordered rules, parameters, randomness, tie preferences,
costs, approximation limits and behaviour at empty/invalid inputs. Identify which
existing units and products change. A new search rule needs explicit acceptance
criteria rather than a promise of a better aggregate score.

1. Define typed contracts and field roles. Specify sample/site/founder axes,
   missingness, units, schema and view lifetimes before writing adapters.
2. Construct independent reference fixtures and negative controls. Cover both
   sides of each decision threshold, whole-class ties, empty cases and a case
   that distinguishes the intended rule from a plausible wrong one.
3. Implement pure transitions and named parameters with provenance. Use explicit
   streams and policies; preserve one arithmetic form per quantity. Declare the
   smallest supported scientific API and kernel signatures.
4. Add stage task/record adapters with explicit dependencies, code roots,
   identities and resource/storage models. Keep scheduling and file effects out
   of science. Validate every equivalent storage route and core count.
5. Add results readers and typed report views. Format outputs without recreating
   scientific choices. Document the unit, parameter reference, output fields,
   costs, limitations and migration impact.
6. Compare complete records and re-decide registered boundaries on both operand
   sets. Resolve undeclared divergences; any approved numerical change needs
   first-divergence, margin and downstream receipts. Run the full relevant checks
   before integrating the new model into command cuts.

A new model version is deliberate. Do not label changed candidates, priors,
random draws, thresholds or release rules as refactoring. Keep truth-based
validation outside inference and never use metadata to bypass an unresolved
scientific decision.
